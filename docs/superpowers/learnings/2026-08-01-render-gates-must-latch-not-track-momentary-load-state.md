# Render gates must latch on first load, not track momentary load state

**Date:** 2026-08-01
**Context:** OmniHarness direct-control conversation UI — unified worker stream fallback gating (`ConversationMain`, `WorkerEntriesManager`, `ConversationTranscriptManager`, `Terminal`).
**Symptom:** After sending a message, the user's bubble appeared and disappeared ~3 times before settling.
**Root Cause:** The just-sent message renders from the legacy `messages` fallback until its `user_input` entry lands in the unified stream. That fallback was gated on `directWorkerStream.isLoaded || conversationTranscript.isLoaded` — both *momentary* signals. `WorkerEntriesManager.isLoaded()` requires `latestContiguousSeq === latestKnownSeq`, so every SSE wake-up (one per appended row, i.e. per streamed text revision) flips it false until the catch-up fetch completes; the transcript's `isLoaded` was `status === "loaded"`, which re-enters `"loading"` on every 2-second poll. Each overlap of the two false-windows closed the gate and removed the fallback bubble from the activity list; each completed fetch re-opened it. The gate's actual purpose — keep stale historical DB rows from rendering before the stream's *first* load — never needed continuous contiguity.
**Fix:**
1. Latched signals: `WorkerEntriesManager.hasEverLoaded()` and `ConversationTranscriptState.hasLoadedOnce` stay true once a validated load completes; the gate now uses those.
2. Messages this client sent itself bypass the gate entirely (`ungatedUserMessageIds` prop on `Terminal`, fed by `locallySentMessageIdsRef`) — a locally sent message cannot be stale history.
3. The bubble now exists from the moment of send: `sendConversationMessage.onMutate` appends an optimistic row (swapped for the server row on success, removed with draft restored on error) and marks it `sending` (dimmed via `data-sending`).
**Verification:** New regression tests: `tests/ui/terminal-user-message-persistence.test.ts` (bubble survives closed gate; no double render after the stream entry arrives; sending marker), latch tests in `tests/app/worker-entries-manager.test.ts` and `tests/app/conversation-transcript-manager.test.ts`, optimistic swap tests in `tests/app/home-utils.test.ts`. All watched failing first. `npx vitest run tests/app tests/ui tests/interface` → 82 files / 625 tests pass; `npm run typecheck` clean.
**Prevention:** When a boolean guards *whether something may render at all*, ask what it actually protects against. "Has the authoritative source loaded at least once" and "is the source fully caught up right now" are different predicates; gating persistent UI on the second one makes content vanish on every incremental refresh. Streams that append continuously (per-token revisions, 2s polls) make momentary loaded-ness flap constantly, so anything derived from it flickers. Content the client itself just created is never "stale history" and should not sit behind staleness gates. Optimistic UI must transition in place (sending → sent → delivered), never be removed and re-added across source handoffs.
