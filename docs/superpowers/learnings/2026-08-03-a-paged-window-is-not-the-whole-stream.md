# A Paged Window Is Not the Whole Stream

**Date:** 2026-08-03
**Context:** OmniHarness direct-control transcript rendering; confirmed with Claude Code session `73fe3ee52059` (1314+ entries, five user turns at seq 1, 646, 647, 930, 1008).
**Symptom:** Every user message in the conversation rendered as one block at the top of the transcript, with all agent output below it, instead of each turn sitting above the output it produced. Reported as a repeat regression: "the ordering WAS LOST, it keeps happening."
**Root Cause:** Two independent defects, both in `src/components/Terminal.tsx`, neither on the write path — the JSONL on disk was correctly ordered the whole time.

1. The transcript loads a bounded tail page (the last ~100 entries). The `messages`-table fallback asked "does the stream already contain this row?" against only the loaded page. Every `user_input` entry older than the window was invisible to that test, so all five rows were re-injected as fallback bubbles. A fallback row has no `seq`, so it borrowed one by anchoring to the first loaded entry not older than it — which, for a window postdating all of them, is the *same* entry. Five messages, one fractional seq, one block. The gate that was supposed to prevent this (`allowUserMessageFallback`) only asks whether the stream has *ever* loaded, which says nothing about whether the loaded window covers where the row belongs.
2. The final comparator chose between `seq` and timestamp *per pair*, falling back to timestamp whenever either side lacked a `seq`. That is not a total order — items A(seq 1, late), B(no seq, mid), C(seq 5, early) form a cycle — so the result depended on which pairs `Array.prototype.sort` happened to compare. This is the mechanism behind the "it comes back in a different shape every time" character of the bug.

**Fix:** A `messages` row is placeable only when its absence from the window is *provable*: the row is newer than the oldest loaded entry, the whole history is loaded (`hasMoreHistory` false), or this client sent it itself. Otherwise it stays hidden until its page loads and brings the real entry, carrying the real `seq`, with it. Fallback rows are placed as a batch (`assignFallbackUserMessageSeqs`) so rows sharing an anchor spread across `(anchor - 1, anchor)` in send order instead of collapsing. Every activity item is reduced to one scalar order key up front (`assignActivityOrderKeys`) so a single total order drives the sort.
**Verification:** `tests/ui/terminal-paged-history-user-message-order.test.ts` reproduces the stacking from the session's real shape and fails first (rendered HTML showed all five turns in one block above the output). Also verified against the live session's actual JSONL and `messages` rows: with a tail window, no earlier turn is stacked in; with full history, the five turns render at strictly increasing positions separated by 53k / 36 / 36k / 11k characters of agent output — the 36-character gap is real, the user did send two messages back to back. `tests/ui/` + `tests/integration/` pass (225 tests); `tsc --noEmit` and `eslint` clean. Four unrelated failures in `tests/server/agent-runtime/` and `tests/lifecycle/` were confirmed pre-existing by re-running them against the stock `Terminal.tsx`.
**Prevention:** "Not in the data I have" is not "not in the data." Any reconciliation between a paginated source and a fallback source must gate on whether the loaded window *covers* the position in question, not on whether the source has loaded at all. And a comparator that picks its sort key per pair is a bug even when it looks like it works: derive one scalar key per item before sorting, so ordering cannot depend on comparison order.
**Skill/Doc Updates:** Added the window-coverage rule to `docs/architecture/worker-conversation-stream.md`, next to the existing fallback rule for legacy `messages` rows, which stated the right principle but was defeated by pagination.
