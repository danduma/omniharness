# Effort Selection Must Follow Runtime and Pair Ownership

**Date:** 2026-09-05
**Context:** OmniHarness Codex ACP launches and composer effort persistence
**Symptom:** A Codex worker could display or run with `low` effort even when the selected session had been changed to another effort. Session `519655bacee0` correctly persisted the later `medium` correction, so the original `low` value was not expected to remain in its database records.
**Root Cause:** The normal Codex fallback launched `codex-acp` with empty arguments, silently discarding the selected model and effort that had only been assembled into native CLI arguments. The ACP adapter reads its initial session configuration from `CODEX_CONFIG`, so the native default could win. Separately, the composer persisted the current effort whenever the worker/model pair changed before hydrating that pair's saved value, allowing an effort selected for Fable to be written into a subsequent Codex pair. The manager also only recognized Claude's `effort` config id, so it could not observe or correct Codex ACP's `reasoning_effort` option.
**Fix:** Pass selected Codex model and effort through `CODEX_CONFIG` using the native `model` and `model_reasoning_effort` fields while preserving other config values, and read/apply Codex's `reasoning_effort` ACP option. Make effort persistence hydrate a new worker/model pair before writing it, and let a fully hydrated run selection authoritatively repair the pair's stored value.
**Verification:** `pnpm test tests/ui/composer-shell.test.ts tests/app/home-utils.test.ts tests/app/run-selection-effects.test.ts tests/server/agent-runtime/codex.test.ts --run` (95 passed); `pnpm build:interface:web`; scoped shared/runner/interface TypeScript checks; scoped ESLint; `git diff --check`. The repository-wide `pnpm typecheck` remains blocked by the unrelated pre-existing error in `tests/app/conversation-transcript-retention.test.ts`.
**Prevention:** When a launcher has an adapter-specific transport, verify the actual child-process environment and ACP/session configuration rather than only the persisted request. For pair-scoped UI preferences, never persist a value during a key transition until that key has been read; server-hydrated session state must be the authority when available.
**Skill/Doc Updates:** No general skill update was needed; existing systematic-debugging, control-plane, and verification guidance already expresses the reusable process, while this note captures the OmniHarness-specific transport and storage details.
