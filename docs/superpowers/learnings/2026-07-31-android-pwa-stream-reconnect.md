# Android PWA Stream Reconnect Is Not Server Offline

**Date:** 2026-07-31
**Context:** OmniHarness Vite PWA, multi-server connection state, Cloudflare Tunnel authentication
**Symptom:** Chrome on Android loaded the newest interface and reached authenticated APIs, but the server switcher reported the server as Offline. After resuming the app, a CLI session could remain Connection degraded until the user clicked Retry. Fresh password login through the configured HTTPS tunnel was also rejected as cross-site.
**Root Cause:** The web runtime treated every EventSource `error` event as terminal, explicitly closed the stream, and let `RunnerConnection` classify the whole server as offline. Chrome on Android can emit a transient EventSource error while it is automatically reconnecting after a mobile network or PWA lifecycle interruption. Even after preserving that reconnecting stream, Android can restore a page with the native EventSource indefinitely stuck in its reconnecting state; the app had no foreground lifecycle transition that explicitly retried a recoverable connection. Separately, the standalone HTTP adapter reconstructs an internal HTTP request URL, so same-origin password login did not recognize the explicitly configured HTTPS public origin unless the proxy was broadly trusted.
**Fix:** Keep EventSource alive while its `readyState` says it is reconnecting, represent that state as degraded, and restore Online when the stream reopens. Start a bounded fallback retry when native reconnect begins and cancel it if EventSource reopens first. On `visibilitychange` to visible, `pageshow`, or browser `online`, explicitly retry server connections already classified as degraded or offline. Reserve Offline for terminal stream/bootstrap failures and do not retry states that require user action, such as reauthentication. Accept the exact `OMNIHARNESS_PUBLIC_ORIGIN` as a same-origin login origin without trusting arbitrary forwarded headers.
**Verification:** Red-green regression tests in `tests/runtime-api/web-runtime-api.test.ts`, `tests/interface/runners/runner-connection.test.ts`, `tests/interface/runners/runner-registry.test.ts`, `tests/interface/runners/runner-browser-lifecycle.test.ts`, and `tests/auth/guards.test.ts`; wider auth/runtime/PWA tests; `tests/interface/pwa-playwright.test.ts`; TypeScript checks; a real Cloudflare request using an Android user agent that completed password login, authenticated bootstrap, SSE first-frame delivery, and logout cleanup.
**Prevention:** Model bootstrap reachability, authentication, event-stream reconnect, app foreground recovery, and terminal network failure as different states. Never close a browser EventSource merely because it emitted `error`; inspect whether the browser is already reconnecting. Do not rely indefinitely on the browser's native reconnect after a mobile app resumes: visible-page lifecycle events must explicitly retry connections in recoverable states, and reconnecting streams need a cancellable fallback timer in case lifecycle-event ordering races the stream error. For reverse-proxy authentication, test the real public HTTPS origin against the standalone adapter rather than relying only on localhost or trusted-forwarder tests.
**Skill/Doc Updates:** No general skill update was needed. The existing client/server-state and lifecycle documents already require explicit reconnect, degraded, and offline states; this note records the concrete failure mode and regression coverage.
