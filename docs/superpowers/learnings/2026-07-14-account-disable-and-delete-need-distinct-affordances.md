# Account Disable And Delete Need Distinct Affordances

**Date:** 2026-07-14
**Context:** OmniHarness Settings, agent account management
**Symptom:** Disabled accounts appeared crossed out, the power button looked unchanged while saving, and users had no way to remove stale test accounts.
**Root Cause:** The interface used deletion-like styling for a reversible disabled state, gave no visible pending feedback, and exposed only the account update route even though persisted account data had several dependent tables.
**Fix:** Disabled accounts now carry an explicit label without a line-through, enable/disable actions show progress, and an inline two-step delete action calls a DELETE route that clears account-owned records and stale run preferences while preserving run and worker history. Each deletion has its own persisted marker, so simultaneous deletes cannot overwrite one another, and account refresh checks those markers again before it finishes. That refresh also clears account links written just after deletion. Success, refusal, and failure decisions emit named events.
**Verification:** Account route tests cover dependent-record cleanup, history preservation, success events, missing-account refusal events, deletion persistence, an account recreated during refresh, and a late run preference pointing to a deleted account. Settings and locale tests cover the translated controls. The live Settings → Agents screen was used to delete 14 test accounts, after which SQLite and the rendered account list both contained zero `test-account-*` records.
**Prevention:** Treat disable and delete as separate state transitions with separate visual language. Before adding a delete route, enumerate every foreign-key and soft reference, define what history must survive, store concurrent deletion markers independently, add named success and failure events, and test the full dependency set plus refresh races.
**Skill/Doc Updates:** The lifecycle contract and `AGENTS.md` now explicitly allow `accountId` as the subject of account-only `error.surfaced` events. This avoids mislabeling an account id as a conversation id while preserving the rule that every user-relevant failure carries a stable subject id.
