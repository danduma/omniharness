# Missing Runtime Agent Is a Recovery Signal

**Date:** 2026-09-06
**Context:** OmniHarness direct-worker messaging, queued interrupts, and runtime restart recovery
**Symptom:** A user saw `Ask failed: Agent not found` after the persisted worker survived a runner/runtime restart. A concurrent recovery attempt could then fail with `Agent is already starting`, leaving the run failed even though another recovery attempt successfully recreated the worker moments later.
**Root Cause:** Queued interrupt delivery emitted its user-facing failure before invoking recovery, left a checkpoint row that would collide on retry, and requeued the input without triggering redelivery. Direct-worker recovery also understood `agent already exists` as an idempotent spawn collision but did not recognize the runtime's `agent is already starting` response or the short interval in which the replacement still returned 404 from `GET /agents/:id`. The runtime itself incorrectly emitted `error.surfaced` for that expected collision.
**Fix:** Missing-agent interrupt failures now enter recovery without emitting `error.surfaced`, remove the retry-colliding checkpoint, requeue, retarget, and immediately redeliver the message. Direct messaging and the recovery reconciler treat both duplicate-spawn responses as an in-progress recovery, use bounded polling to adopt the replacement agent, and fence polling and persistence against newer turns and Stop. Stop advances the worker generation, recovered queue draining refuses stale generations, and the runtime records a typed coalescing event instead of surfacing the collision as an error.
**Verification:** Reproduced the queue failure, saved-session redelivery gap, concurrent-spawn failure, runtime event leak, registration lag, stale-turn race, and hanging lookup with regression tests. Focused direct-message, queue, recovery, runtime, and lifecycle suites all passed.
**Prevention:** Treat persisted-worker/runtime-agent disagreement as a recoverable lifecycle state. Perform recovery before recording user-visible failure, make spawn idempotency include both “exists” and “starting,” and account for registration lag before querying a concurrently spawned agent.
**Skill/Doc Updates:** No shared skill update was needed: the existing control-plane guidance already requires recovery paths and user-relevant errors to be distinguished. This project note captures the concrete OmniHarness invariant and test coverage; the architecture specification was not changed because it already states the governing rule and had unrelated in-progress edits.
