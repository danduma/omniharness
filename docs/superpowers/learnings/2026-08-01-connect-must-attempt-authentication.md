# Connect Must Attempt Authentication

**Date:** 2026-08-01
**Context:** OmniHarness server profiles, saved passwords, and browser/native authorization
**Symptom:** Entering the server password in Edit server and pressing Connect initially closed the dialog but left the interface on the password screen. After that action was fixed, it worked only when repeated manually; clearing or losing the browser session and reloading still showed the password screen even though the profile retained the password.
**Root Cause:** The edit flow treated an unchanged saved password as evidence that authorization did not need to run. Native profiles therefore skipped direct login when a saved password matched the submitted value, even if their bearer credential was missing, expired, or revoked. The same-origin browser profile returned from the authorization function without using the submitted password at all. Fixing that button exposed a second path with the same mistaken model: startup loaded the saved password but never exchanged it for a server-authoritative cookie session. Profile persistence and authentication state had been conflated in both entry points. Separately, the production runner reads and retains `dist/interface/index.html` at startup, so rebuilding the interface without restarting the runner leaves the public domain serving the old hashed JavaScript bundle.
**Fix:** The current same-origin profile now submits the password through its runtime login endpoint and retries its connection when Connect is pressed. On startup, an unauthenticated same-origin profile with a saved password makes one login attempt, reloads bootstrap to prove the server accepted it, and then connects normally. A rejected password stops at `needs-reauth` without an automatic retry loop. Native profile edits authorize whenever Connect is submitted with a password, regardless of whether the saved password text changed. After rebuilding, the existing production runner was restarted through the restart controller so it loaded the new interface manifest.
**Verification:** Both focused regression tests were observed failing before their respective fixes and passing afterward. `pnpm vitest run tests/interface/runners/runner-connection.test.ts tests/ui/sidebar-layout.test.ts` passed 56 tests, TypeScript passed, changed-file lint passed, and the web interface built. The targeted Playwright journey `automatically unlocks the current server with its saved password after reload` passed against two temporary real runners after clearing the browser cookie and reloading. After the production restart, the public domain and local build both referenced `main-DWX2wW4Q.js`, and their SHA-256 hashes matched exactly (`c08dcaf7094335ae85afa8956be76af74d851928f88b978a699b2b4f39f5a857`).
**Prevention:** Treat Connect as an explicit authentication attempt, and treat reload as a separate return journey that must restore server-authoritative authentication from saved credentials. Decide whether to authenticate from connection and credential state plus the user's action, never from a comparison of secret text. Regression coverage must test every authentication entry point, assert that the password reaches a real login path, clear the server session, revisit the app, and verify that startup restores it without manual UI actions. For live interface changes, rebuild and restart the production runner, then compare the public asset name and hash to the local build before reporting the fix as live.
**Skill/Doc Updates:** No general skill update was needed because the existing client/server state guidance already says persisted client data cannot stand in for server-authoritative state. This project note and regression test make the authentication-specific case durable.

## Follow-up: cold mobile startup and live build isolation

**Date:** 2026-08-03
**Symptom:** A newly opened or reinstalled mobile PWA first showed a blank screen and, after the live runner was restarted, accepted the password but showed the generic “The server operation failed. Try again.” message.
**Root Cause:** The interface build test wrote directly to `dist/interface`, replacing the hashed JavaScript assets while the production runner still held the previous `index.html` in memory. That made the old asset URL return 404 for a fresh PWA. After the runner restart exposed the current build, separate cold-start races remained: the same-origin Connect handler first required `RunnerConnection` to have already attached its runtime. Once that was removed, an offline retry timer could still start while the explicit login request was in flight, replace the connection generation, and cause the client to discard a server-successful login as stale without making the authenticated reconnect.
**Fix:** Vite build tests now use unique operating-system temporary output directories through `OMNIHARNESS_INTERFACE_OUT_DIR`, so the test suite cannot modify live assets. Same-origin password authentication now belongs to `RunnerConnection`; it supersedes the previous connection generation, cancels the pending retry timer, creates or reuses the runtime, checks the base URL before and after login, and then reconnects. The React control no longer reaches into a partially initialized runtime, and a background retry cannot outrank the user's explicit Connect action.
**Verification:** Both cold-start regressions were observed failing before their fixes and passing afterward. The focused connection and UI suites passed 58 tests after the retry-timer race was added. The isolated Vite suite passed all 3 tests while pre/post hashes proved `dist/interface` remained unchanged. TypeScript and changed-file lint passed. The rebuilt production runner served the current hashed asset through Cloudflare with HTTP 200 and the same SHA-256 hash as the local asset; public auth-session and bootstrap endpoints returned 200. A fresh Android-sized headless Chromium context with no cookie and a saved password recorded bootstrap 200, login 200, authenticated bootstrap 200, and event-stream 200, then remained on the working app for 12 seconds and logged out cleanly.
**Prevention:** A test must never build into a directory served by a long-running process. Authentication transitions must be owned by the connection manager and tolerate cold initialization; components should not require an asynchronously attached runtime as a precondition for the user’s explicit Connect action. Timers must re-check ownership, and an explicit user transition must cancel or supersede background work before awaiting network I/O.
