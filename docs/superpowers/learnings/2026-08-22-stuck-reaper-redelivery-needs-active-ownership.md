# Stuck-Reaper Redelivery Needs Active Ownership

**Date:** 2026-08-22
**Context:** OmniHarness direct-control stuck-worker recovery, session `054dc5ddea78`
**Symptom:** The reaper recreated the worker and re-delivered the interrupted prompt, and the agent continued working, but the persisted worker/run showed `idle`/`done`. The conversation therefore looked stopped and could be reaped or restarted again while the recovered turn was still active.
**Root Cause:** `resumeMissingDirectWorker` correctly reconciled the newly attached bridge agent as idle. The reaper then called the long-running `askAgent` directly without first reclaiming durable ownership, so no active status or continuation-started event covered the interval between redelivery and completion. A redelivery failure also only marked the worker as errored and could leave the run terminal as `done` with no user-visible failure.
**Fix:** Before redelivery, the reaper now uses the shared Stop/recovery mutation fence to generation-check the worker, persist `worker=working` and `run=running`, and emit `worker.recovery_continuation_started`. Completion and failure settlement are generation-guarded; stale or aborted continuations emit `worker.recovery_continuation_superseded`, while genuine delivery failures set the worker/run to `error`/`failed` and emit `error.surfaced` with `worker.resume.failed`.
**Verification:** The unit regression was observed failing with `idle` instead of `working` and `done` instead of `failed`, then passing after the fix. `tests/lifecycle/scenarios/stuck-direct-worker-redelivery.test.ts` mirrors the incident and asserts active ownership during the pending ask. `pnpm test:lifecycle` passed 52/52 tests, and targeted ESLint passed. Full typecheck remains blocked by two unrelated pre-existing errors in `src/runtime/http/routes/worker-entries.ts`.
**Prevention:** Every recovery path that starts a full agent turn must publish durable active ownership before the external await, use the worker generation as a stale-callback fence, and explicitly settle both success and failure. Tests must inspect state while the ask is still pending, not only after it resolves.
**Skill/Doc Updates:** No general skill or architecture update was needed. `docs/superpowers/learnings/2026-08-16-long-awaits-need-a-busy-status-first.md` already states the general rule, and the lifecycle observability architecture already requires named decisions and surfaced failures. This incident adds enforcement at the previously uncovered stuck-reaper call site.
