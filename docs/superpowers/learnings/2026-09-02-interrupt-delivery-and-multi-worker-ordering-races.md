# Interrupt Delivery and Multi-Worker Ordering Need Stable Boundaries

**Date:** 2026-09-02
**Context:** Direct-conversation interrupt delivery and unified worker-stream rendering
**Symptom:** In session `56b9ea73fe06`, an interrupted message was recorded as delivered even though the worker only emitted cancellation leftovers. A later edit recovery created a replacement worker, whose output briefly appeared above the earlier conversation and then moved into the correct position after a refresh.
**Root Cause:** Interrupt delivery aborted the local turn but started the replacement provider request before the provider-side cancellation had settled. The delivery check then treated any later non-user stream text, including revisions of an old tool call and lifecycle metadata, as proof that the replacement prompt received a response. Separately, the UI decided whether to use multi-worker timestamp ordering from the transcript worker list alone; the current worker snapshot learned about the replacement first, leaving a short window where entries from two independent sequence spaces were sorted as if they belonged to one worker.
**Fix:** Keep the interrupt API responsive, but make its background delivery wait for provider-side cancellation before sending the replacement prompt. Only accept response-bearing stream entries that belong after the new input, excluding revisions and tool updates whose identity existed before the input. Determine multi-worker ordering from the union of the current worker snapshot and transcript worker lists so a stale transcript refresh cannot switch the ordering rule.
**Verification:** `pnpm exec vitest run tests/app/direct-worker-stream-loading.test.ts tests/server/queued-message-interrupt.test.ts tests/ui/terminal-unified-stream-order.test.ts tests/api/conversation-messages-route.test.ts` (81/81); `pnpm exec vitest run tests/lifecycle/scenarios/direct-initial-steer.test.ts` (3/3).
**Prevention:** Treat provider cancellation as a required boundary before replacement provider I/O, and never infer turn ownership from append order alone. For merged worker streams, decide the ordering mode from worker identity state that arrives earliest and keep that mode stable while transcript pages catch up.
**Skill/Doc Updates:** No general skill update was needed; the lifecycle architecture already requires explicit turn ownership and stable client/server state, and this note records the concrete interrupt and ordering invariants.
