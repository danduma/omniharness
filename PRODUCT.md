# Product

## Register

product

## Users

Software developers and technical leads supervising several coding agents across local, remote, desktop, editor, and mobile surfaces. They work in long-running implementation and debugging sessions where clear state, rapid switching, durable recovery, and trustworthy control matter more than decorative presentation.

## Product Purpose

OmniHarness is a durable control plane for starting, observing, steering, and recovering ACP-backed coding-agent work. Success means a user can understand what every runner and worker is doing, take the next safe action quickly, move between devices and servers without losing context, and trust that failures, credentials, and recovery states are represented honestly.

## Brand Personality

Calm, capable, direct. The interface should feel like a precise professional tool with a human voice: dense when the work demands it, quiet when it does not, and explicit about uncertainty or failure.

## Anti-references

- Generic analytics dashboards built from interchangeable metric cards.
- Sci-fi command centers with neon decoration, fake telemetry, or gratuitous motion.
- Chat interfaces that hide execution state and recovery controls behind conversational chrome.
- Consumer onboarding that stretches a simple connection task into a promotional sequence.
- Interfaces that make remote, offline, authentication, or identity failures look like temporary loading.

## Design Principles

1. Show authority and scope. Every action, status, notification, and cache belongs visibly to one runner and one conversation.
2. Keep supervision fast. Frequent actions remain close to the active work, with familiar controls and strong keyboard behavior.
3. Make failure honest and recoverable. Name the affected runner, explain the state, and offer the smallest safe next action.
4. Preserve context across time and surfaces. Switching, reconnecting, and returning later should not erase drafts, cursors, or the user’s mental model.
5. Let the work dominate. Navigation and status remain legible but visually restrained around agent output, terminal content, and decisions.

## Accessibility & Inclusion

Target WCAG 2.2 AA. All flows must support keyboard navigation, visible focus, screen readers, zoom and narrow layouts, live language changes, reduced motion, and status communication that does not rely on color alone.
